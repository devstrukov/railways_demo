# Задание агенту: лабораторная № 3 «Создание элементов пользовательского интерфейса»

## Цель и главный приоритет

Реализуй небольшое, полностью работающее учебное приложение для существующей PostgreSQL-базы железнодорожного агрегатора. SQL-дамп приложен отдельно и является источником истины для структуры таблиц, типов, ограничений и связей.

Главный приоритет — максимальная простота реализации, запуска и понимания кода. Нужен стандартный интерфейс для демонстрации лабораторной, без продуктовой разработки и лишних возможностей. Доведи приложение до рабочего состояния, проверь сборку и основные сценарии. Не останавливайся на плане или макете.

## Стек и архитектура

- Frontend: React + Vite + JavaScript. Не Next.js, без SSR.
- Backend: Java 21 + Spring Boot, Maven Wrapper.
- База: PostgreSQL 18, существующая схема из дампа.
- Один frontend, один backend, одна база. Обычный HTTP JSON API.
- UI: стандартный Bootstrap CSS, установленный через npm; обычные HTML-элементы. Без отдельной библиотеки React-компонентов.
- Frontend обращается к API через встроенный `fetch`; Vite проксирует `/api` на backend.
- React: функциональные компоненты, `useState`, `useEffect`. Без Redux, Zustand, React Query, Axios и сложной системы хуков.
- Backend: Spring Web + JDBC (`NamedParameterJdbcTemplate`) + Validation + драйвер PostgreSQL. Прямые параметризованные SQL-запросы; без JPA/Hibernate.
- Простейшие классы Controller → Repository. Service добавляй только при реальной необходимости, без интерфейсов с единственной реализацией. Для DTO подходят Java records.
- Для переключения трёх экранов достаточно вкладок и состояния в `App`, без React Router. Печатный отчёт можно открывать отдельным режимом через query-параметр.
- Не добавляй авторизацию, регистрацию, JWT, микросервисы, брокеры, кеш, DDD, CQRS, MapStruct, Lombok, генераторы CRUD, OpenAPI, миграции и универсальные абстракции.
- Реальные покупки билетов, интеграции с РЖД, платежи и отправка уведомлений не входят в задание.

## Подключение существующей базы

1. Сначала изучи дамп. Не придумывай отсутствующие поля или связи.
2. Не изменяй состав таблиц и атрибутов. Не исправляй модель предметной области в рамках этой задачи. Не пересоздавай и не очищай существующую базу.
3. Настройки подключения backend передавай переменными окружения с локальными значениями по умолчанию. Добавь `.env.example` и объясни, как передать эти значения процессу Java: Spring Boot сам по себе не читает `.env`.
4. Должны поддерживаться два варианта: подключение к уже работающей БД и отдельная учебная БД в Docker Compose. Compose нужен только для PostgreSQL; frontend и backend запускаются локально.
5. Для отдельной БД используй роль `test`, поскольку дамп содержит `OWNER TO test`. Покажи команду импорта оригинального дампа через `psql` с `ON_ERROR_STOP=1`. Дамп содержит `COPY` и команды psql, поэтому не загружай его через JDBC и не используй как `schema.sql`.
6. Импорт — только явная команда для новой пустой учебной базы. Не выполняй его автоматически при каждом запуске приложения.
7. Не подменяй БД mock-данными. Учитывай nullable-поля и бронирования без билетов.

## Что необходимо реализовать

Все надписи интерфейса — на русском. Предусмотри три вкладки: «Пользователи», «Бронирования», «Подробное бронирование».

### 1. Ленточная форма «Пользователи»

Источник — `users`, название роли брать из `role`.

- Покажи несколько пользователей одновременно. Каждая запись — повторяющаяся горизонтальная полоса с обычными подписанными полями: ФИО, email, телефон, роль.
- Это именно повторяющиеся формы с полями ввода, а не вторая HTML-таблица и не сетка карточек.
- Роль выбирается из списка с названиями, в БД сохраняется её ID.
- Для каждой записи достаточно кнопок «Сохранить» и «Отменить». Сохраняются только ФИО, email, телефон и роль; `updated_at` обновляется при успешной записи.
- Не показывай и не передавай в API `password_hash`. Не добавляй создание пользователей и управление паролями.

### 2. Табличная форма «Бронирования»

Источник — `booking`, связанные `users` и `booking_status`.

- Обычная HTML-таблица: номер бронирования, пользователь, статус, сумма, дата и действие «Открыть».
- ФИО и название статуса выводятся вместо числовых внешних ключей. Если пользователь не задан, выводи «Не указан».
- «Открыть» переключает на подробную форму выбранного бронирования.
- Достаточно просмотра; редактирование выполняется в подробной форме.
- Без пагинации, сложных фильтров и сортировок: данных в учебном дампе немного. Задай устойчивый порядок записей SQL-запросом.

### 3. Сложная форма «Подробное бронирование» с подчинённой формой

Главная запись — `booking`, подчинённые записи — `ticket`, связь `ticket.booking_id = booking.id`.

- Вверху список выбора бронирования с понятной подписью, например «№ 1 — Иван Петров».
- Основная форма: номер (только чтение), пользователь (список), статус (список), сумма, дата бронирования (только чтение).
- Позволь изменить пользователя, статус и сумму. Для nullable `user_id` предусмотрена опция «Не указан».
- Кнопки «Сохранить», «Отменить», «Печатный отчёт».
- Внизу размести явно подписанную подчинённую форму «Билеты бронирования» в виде простой таблицы.
- Для билетов покажи номер, ФИО пользователя билета и название перевозчика через `train_operator`. Не выдумывай маршрут, место или пассажира: таких связей у билета в текущем дампе нет.
- При смене бронирования автоматически загружаются только его билеты. Не должно быть ситуации, когда показаны билеты предыдущей записи. Для отсутствующих билетов выводи «Билетов нет».
- Билеты доступны для просмотра; CRUD билетов не требуется.
- При переходе с несохранёнными изменениями достаточно стандартного `window.confirm`.

### 4. Печатный отчёт с подчинённым отчётом

Это отдельное представление данных для печати, а не учебный отчёт о выполнении лабораторной.

- Открывается из сложной формы кнопкой «Печатный отчёт» для текущего бронирования. Если есть несохранённые изменения, попроси сначала сохранить или отменить их.
- Главный блок отчёта: номер бронирования, пользователь, статус, сумма и дата.
- Внутри главного блока — подчинённый отчёт «Билеты бронирования» с таблицей билетов только этого бронирования.
- Используй те же данные и связь, что в сложной форме. При отсутствии билетов покажи понятную надпись.
- Добавь заголовок и примечание с ФИО студента и группой. Фамилия: Стрюков; группа: з-435п8-4. Полное ФИО не выдумывай: вынеси в одну настройку с явной отметкой, что её надо заполнить перед сдачей.
- Реализация: обычный React-компонент, печатные CSS-стили и `window.print()`. Без PDF-библиотек, JasperReports и серверной генерации документов.
- Формат A4, белый фон, чёрный текст. При печати скрывай навигацию и кнопки, предотвращай обрезание столбцов и ненужные пустые страницы. По возможности повторяй заголовок таблицы при переносе.
- Предусмотри кнопки «Печать» и «Назад». Пользователь может сохранить PDF стандартными средствами браузера.

## Минимальный API

Достаточно следующих маршрутов; не создавай API для всех таблиц дампа:

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/api/users` | Пользователи с названием роли, без хеша пароля |
| PUT | `/api/users/{id}` | Изменение разрешённых полей пользователя |
| GET | `/api/roles` | Список ролей |
| GET | `/api/booking-statuses` | Список статусов бронирования |
| GET | `/api/bookings` | Бронирования с именем пользователя и названием статуса |
| GET | `/api/bookings/{id}` | Подробности бронирования и массив его билетов |
| PUT | `/api/bookings/{id}` | Изменение пользователя, статуса и суммы |

Печатный отчёт использует тот же GET подробностей. Отдельный API отчётов не нужен. Представления из дампа использовать необязательно: простые JOIN допустимы.

## Минимальные требования к корректности

- Все SQL-параметры передаются параметризованно.
- Денежные значения обрабатываются на Java как `BigDecimal`, в БД остаются `numeric`. Для ввода используй десятичную строку и передавай сумму строкой, не выполняй расчёты денег через JS floating point.
- Проверь обязательные поля, формат email, неотрицательную сумму, максимум два знака после запятой и ограничения существующих колонок. Не изобретай дополнительные бизнес-правила.
- Backend проверяет существование переданных внешних ключей либо корректно обрабатывает нарушение FK. Ошибка уникальности email возвращается понятным сообщением.
- Для отсутствующей записи возвращай 404, некорректных данных — 400, конфликта уникальности — 409. Достаточно простого JSON `{ "message": "..." }` и одного обработчика ошибок.
- На frontend нужны состояния загрузки, пустого списка, ошибки и успешного сохранения. На время сохранения отключай кнопку.
- API обновляет только явно разрешённые поля, а не произвольные колонки из запроса.
- Даты с часовым поясом отображай понятно и одинаково на экране и в отчёте; не теряй timezone при чтении. Редактирование дат не требуется.
- Отмена восстанавливает значения последней загрузки/сохранения. После сохранения показывай актуальные данные из базы.

## Оформление

Стандартная светлая административная страница: контейнер Bootstrap, заголовок, вкладки, поля ввода, select, таблицы, обычные кнопки и сообщения. Без анимаций, графиков, градиентов, иллюстраций, кастомной дизайн-системы, дашборда и боковой панели. Аккуратные отступы и читаемые подписи. Ленточная форма и табличная форма должны визуально различаться. На узком экране таблицы могут прокручиваться горизонтально.

## Результат и проверка

Передай исходники в двух каталогах `frontend/` и `backend/`, Compose для отдельной учебной БД, примеры конфигурации и короткий `README.md`. Не создавай многочисленные документационные файлы.

В README укажи:

1. Требования к Java, Node и PostgreSQL; версии должны соответствовать выбранным зависимостям.
2. Точные команды импорта дампа, подключения к существующей БД и запуска backend/frontend.
3. Адреса и порты приложения; не занимай существующий PostgreSQL-порт без необходимости.
4. Где задать полное ФИО и группу для печатного отчёта.
5. Краткое соответствие элементов приложения требованиям лабораторной.
6. Сценарий скринкаста: показать ленточную форму и сохранение → табличную форму → открыть бронирование → изменить статус/сумму → переключить бронирование и показать изменение списка билетов → открыть отчёт → показать предварительный просмотр печати.

Критерии приёмки:

- Frontend собирается, backend собирается и запускается; результат проверок сообщён честно.
- Приложение работает с приложенным дампом без изменения схемы.
- Все три вида форм реализованы, данные читаются из реальной БД.
- Изменения пользователя и бронирования сохраняются и остаются после обновления страницы.
- Связанные названия показываются вместо числовых FK; хеши паролей не попадают в ответы.
- Подчинённая форма и подчинённый отчёт содержат только билеты выбранного бронирования.
- Работают отмена изменений, пустое бронирование и сообщения об ошибках.
- Печатный отчёт корректен в предварительном просмотре браузера.

Проверь перечисленные сценарии на отдельной учебной БД, не меняя пользовательскую базу без необходимости. Не добавляй большой тестовый фреймворк ради этой лабораторной. Если окружение не позволяет проверить БД или браузер, явно перечисли непроверенное; не утверждай, что всё проверено.

Не нужно генерировать учебный отчёт DOCX/PDF и записывать скринкаст: сейчас нужны работающее приложение и инструкция для их последующей подготовки. При рутинных технических решениях выбирай самый простой вариант и продолжай работу самостоятельно.
